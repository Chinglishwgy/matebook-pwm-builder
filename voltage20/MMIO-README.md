# MateBook X Pro 2021 MMIO PL1 = 20W — one-reboot upgrade

**Experimental; NOT yet validated on your exact machine.** Requirements:
- Intel i7-1165G7 (Tiger Lake-U, CPU family 6 model 0x8C)
- macOS Sequoia 15.8.1, OpenCore, current VoltageShiftSecure MSR 20W helper already installed
- AC power, backup bootable USB EFI for recovery, stable hardware cooling

## Why this exists
The previous MSR PL1 writer successfully read back 20W, but CPU package power remains ~9.96W at all-core load. The MMIO package RAPL limit is a possible independent limiter.

## Hardware access and safety checks
- Read-only operation: 'sudo /usr/local/libexec/matebook-pl1/voltageshift mmio-read'
- Guarded change: 'sudo /usr/local/libexec/matebook-pl1/voltageshift mmio20'
- PCI host bridge **00:00.0** must be Intel, MCHBAR must be enabled, 32-bit, in an expected physical MMIO range, and must map successfully.
- MCHBAR + **0x59A0** is the Intel package RAPL MMIO register (low32 PL1, high32 PL2), based on Linux Intel Xe and setPL source references.
- MSR 0x606 supplies power units; only permitted CPU family/model 6:0x8C; exponent range checked.
- No writes when MMIO lock bit63 set, PL1 disabled, current PL1 outside 5-28W, or current PL1 already >=20W.
- MMIO writer only changes low 15 bits of the low 32-bit PL1 word, and verifies readback. All other bits (PL1 enable, clamp, time window, PL2, lock) are preserved.
- Does **not** touch BIOS, EC, MMIO Lock, BD_PROCHOT, undervolting or voltage controls.
- Continues to rely on CPU/firmware thermal shutdown and other power protections.
- MMIO read success or MMIO20_OK **does not guarantee actual package power will reach 20W**; there may be further EC, current, VR or thermal constraints.

## One reboot deployment
1. Obtain a successfully compiled GitHub Actions artifact 'MateBook-MMIO-PL1-20W-Experimental'. Unzip both layers and enter the 'MateBook-MMIO-20W' folder.
2. Ensure a known-working bootable USB EFI is available. Mount the **same OpenCore EFI that actually boots** the machine (commonly '/Volumes/EFI', but not guaranteed). Before proceeding back it up.
3. Run 'bash install-mmio-20w.sh' once. The installer checks the enabled existing VoltageShift Kext and makes a timestamped backup under the desktop. It replaces only VoltageShift.kext and its CLI. It does NOT alter the OpenCore config.plist or your existing WhateverXe backlight, I2C, NVMe etc.
4. Reboot once to activate new kernel extension and launchd. The MMIO helper reads MMIO and attempts safe 20W on AC, with retry every 5 min. Battery power is not modified.
5. Check auto output: 'sudo tail -80 /var/log/matebook-mmio-20.log'
6. Check actual CPU watts with a ~12-second four-core CPU load plus 'powermetrics', without another reboot.

## Rollback
Run 'bash rollback-mmio-20w.sh ~/Desktop/MateBook-MMIO-Backup-YYYYmmdd-HHMMSS' using the exact backup folder generated by installation.
This removes only MMIO daemon, restores the original VoltageShiftSecure Kext and CLI from the backup, and leaves the existing MSR 20W job and other OpenCore entries unchanged. Restart once to reload the original Kext.

If system cannot boot, start from existing backup USB EFI, mount the problematic EFI and restore the previous VoltageShift.kext. This is why a fallback EFI is required.

## Known limitations
- Kernel-level MMIO mapping on Sequoia may fail or be blocked; **this build is experimental**, only static compile can be checked in CI.
- MMIO physical registers may be firmware-managed and revert on AC mode changes or sleep/wake; periodic retry is conservative, but no benefit is guaranteed.
- On MMIO lock detection the tool refuses writing and reports an error. It will never force the lock.
- The original upstream VoltageShiftSecure generally allows arbitrary MSR write operations as root. The added MMIO entry point is limited to READ or 20W, but it doesn't remove pre-existing upstream functionality.
- When thermal problems, fan issues, crashes or sleep/wake regressions occur, stop the daemon and restore the original Kext.
